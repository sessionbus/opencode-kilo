# opencode-kilo v0.5.11

This release moves `opencode-peer` to the OpenCode v2 line and `kilo-peer` to Kilo 7.8.1, and carries the fixes listed below. It pins the Sessionbus Go SDK `v0.5.12`, and both native plugins pin `@sessionbus/kit` `0.5.12`. Native OpenCode and Kilo are installed separately and are not pinned.

The runs behind this release used Sessionbus daemon v0.5.10 (the 2026-10-02 test matrix) and v0.5.11 (every later run). Earlier builds on the way to it ran with daemon v0.5.9, as [KNOWN-ISSUES.md](../KNOWN-ISSUES.md) records; this release itself was not run with v0.5.9. As with v0.5.10, a daemon older than v0.5.9 is not supported (see the flag day in the [v0.5.10 notes](v0.5.10.md)).

**Breaking for OpenCode.** `opencode-peer` now uses the plugin and background-service surfaces of OpenCode v2 and was built and tested against OpenCode 2.0.21. OpenCode 1.18 is no longer a target of this package. `kilo-peer` was tested with Kilo 7.8.1 only.

`scripts/install-opencode.sh` and `scripts/install-kilo.sh` install the latest stable release by default, so they now install v0.5.11. Set `SESSIONBUS_VERSION=v0.5.10` on a host that still runs OpenCode 1.18 or is not in its upgrade window.

**Installing this release over a running OpenCode service.** An install replaces the plugin's files. A running OpenCode service keeps the plugin it has loaded until OpenCode loads plugins again or the service is restarted.
- **To load the installed build, restart the service:** `opencode service restart`. This is OpenCode's own command and it affects every OpenCode session of that user:
  - a shell command still running in a session ends (read in the OpenCode 2.0.21 source), and a lane's running Run ends as `unavailable`;
  - every managed interactive session leaves the bus when the old service process ends. A session whose TUI is open is activated again by that TUI when it reconnects. One without an open TUI stays off the bus until it is activated again, for example by a new `opencode-peer` launch of that session. In the one restart recorded for this release, all 18 sessions of the service were on the bus 60 s later;
  - read in the OpenCode 2.0.21 source: the service is started again by whichever client asks first, the restart command or an open TUI, and it inherits that client's environment.
- **OpenCode can also reload the plugin by itself after an install.** If the plugin still loaded is one of an earlier release, the managed interactive sessions then leave the bus, because that plugin has nothing to hand over. A session whose TUI is still open can be activated again by that TUI's own signals. Lane rows are not affected.
  - At an install on 2026-10-03 this happened: 18 sessions left the bus. None had returned 14 minutes later. All 18 were on the bus again two days later; what brought them back was not recorded.
  - At three installs on 2026-10-11, on the same host, neither a reload nor a session leaving the bus was observed in what was recorded after each: the bus list 10 s after two of them, two sessions sampled for 50 s around the other one, and OpenCode's own log for 10 to 60 s. That is not a record of the whole time after an install. What made OpenCode reload after the one install, and whether it reloaded later after the other three, is not known.

From this release on the plugin hands its sessions to its next instance when OpenCode reloads it (see "Sessions are handed over across a plugin reload" below, and Limits). The hand-off passed its tests against stand-ins. It has not been observed across a real reload on a host: in the one run made for it, no reload was observed.

Upgrade while no OpenCode or Kilo lane is running or starting. A lane worker of an earlier build that is still starting when the first lane of this build starts could lose its tool socket.

## Changes since v0.5.10

### OpenCode

- **Interactive sessions run on the v2 background service** (#14). `opencode-peer` replaces itself with the native TUI, which uses your background OpenCode service. The Sessionbus attachment lives in that service's plugin, not in a separate process.
  - A message is one native steer prompt, and the receipt is `injected` once OpenCode admits it. An idle session starts a new turn with it. A busy session receives it at the next model step of the turn it is running.
  - A managed session stays on the bus while OpenCode keeps it loaded. Closing the TUI does not remove it. Native session deletion does, and so does OpenCode unloading its idle directory (about 60 minutes without activity). A session whose TUI is still open is activated again when OpenCode reloads it.
  - A launch that selects no session gets one. A native rename updates the bus name. Native sub-agent (task) sessions are not peers of their own: where OpenCode lets one use the tool, it speaks as the managed session or lane it descends from.
  - `--standalone` and `--server` (with its value) before `--` are ignored, and the TUI always starts on that service (#22).
- **Lanes are clients of the same background service** (#14), as native `opencode run` is: your logins, history and default model apply.
  - A lane never stops the service. A service restart ends the lane's running Run, which is reported `unavailable`; OpenCode may then continue that turn by itself.
  - A message to a busy lane reaches its current turn at the next model step.
  - With no human present, permission asks and questions in a lane are declined with a message and the model continues, unless the lane was opened with `permission_mode` `bypassPermissions`.
  - A lane whose Sessionbus binding fails is refused at spawn.
- **An interrupted lane Run withdraws its undelivered messages** (#15). Before, a message admitted to the Run but not yet delivered stayed in the native inbox, and the lane's next Run delivered it.
- **A failed product interrupt is reported** (Go SDK v0.5.12). It is answered with the error `product interrupt failed`, and a later interrupt for the same Run reaches OpenCode again. Before, the failure was answered as success.
- **Sessions are handed over across a plugin reload** (#27). OpenCode can reload the plugin inside its running service: after the plugin's files change, as at an install, or when a plugin set up before it changes. Each reloaded plugin instance, one per loaded directory, then dropped the managed interactive sessions it held from the bus. A session whose TUI was still open could be activated again by that TUI's existing signals; the others stayed off the bus until a new activation. Now the plugin hands what it holds to its next instance.
  - An interactive session still leaves the bus and is meant to join it again with no relaunch, under the same ID and groups and the bus name it had. A session that had no bus name comes back under its current title if that title is a valid bus name. The rejoin can fail: the session is then off the bus with nothing shown in its TUI, and needs a new activation.
  - A lane's row belongs to its worker and stays on the bus. Only the connection that carries the lane session's Sessionbus tool is made again, and that tool can fail until it is.
  - A message being handed over to an interactive session at that moment has an uncertain outcome and is never replayed; a send to it while it is away is refused. A Sessionbus tool call pending at that moment, from a managed session or a lane, can fail; what it had already attempted is uncertain, and it is not repeated.
  - If OpenCode reloads the plugin at the install that first brings this build, those sessions still leave the bus once: the outgoing plugin has nothing to hand over. A TUI that is still open can activate its session again by its existing signals, as before.
  - Nothing is handed across an unload of the directory: a session whose directory OpenCode unloads, or that is deleted, leaves the bus as before.
  - Read in the OpenCode 2.0.21 source: the Sessionbus kit is not loaded again on a reload. After an install that brings a new kit, the running service would keep the old one until it is restarted.
  - This rests on OpenCode 2.0.21 giving both plugin instances of a loaded directory the same location object. With a native that does not, sessions drop on a reload as before.
  - Kilo is unchanged. In the Kilo 7.8.1 source read for this change there is no corresponding file-triggered reload.

### Kilo

- **A message to a busy session is shown where it was handed off** (#16). Before, it was stored on the original task message and dated by it; in the recorded cases the model then handled it only after finishing its task, or not at all.
- **After a native abort, a waiting message is held** (#17). When the user cancels with Esc Esc while a message is pending, that message is no longer submitted as a new turn. It is held until native starts work on the session again.
- **A fresh launch is reachable before its first prompt** (#18). A launch that selects no session creates its native session at once, titled with `-n` when given. That session stays in Kilo's session list even if nothing is typed.
- **A displaced session fails at once, with a sentence** (#19, #21, kit 0.5.10). When a second `kilo-peer` launch takes over the same Sessionbus identity, the first session's `sessionbus` tool calls fail with "Sessionbus: another kilo-peer launch took over this session (superseded); relaunch to use Sessionbus here". Before, such a call stayed running with no output.
- **A managed launch without the plugin registration is refused** (#26). `kilo-peer` used to open an ordinary Kilo TUI, with no notice and no bus presence, when the Sessionbus plugin was no longer registered. It now reads the plugin lists in the global Kilo config directory before it starts Kilo. If the server list or the TUI list positively holds no Sessionbus entry, it starts nothing and prints the command that registers the plugin again.
  - Anything it cannot establish proceeds as before: an unreadable or unparsable file, an entry with `{env:...}` or `{file:...}`, a URL, `git:` or aliased entry, a local package that cannot be read, or a plugin file in that directory's `plugin` / `plugins` folder (server list only).
  - A registration kept only outside those global files (a project file, a `.kilo` directory, the `KILO_CONFIG*` or `KILO_TUI_CONFIG` variables, remote or managed config) is not recognised and the launch is refused.
  - A fresh or throwaway `HOME` or `XDG_CONFIG_HOME` with positively absent global registrations is refused before Kilo starts.
  - Not detected: a plugin that is registered but switched off in Kilo, or that fails to load. OpenCode has no such check.

### Both products

- **A killed lane worker's tool socket is cleaned up on Linux** (#25). A lane worker that is killed without closing (for example by SIGKILL) used to leave its tool socket file in the Sessionbus runtime directory. Now, on Linux, the next OpenCode or Kilo lane worker to start on that host removes it.
  - On macOS nothing changes: a refused connection there does not prove the worker is gone, so the file stays.
  - A worker killed during its own startup can still leave a `t-` socket file.
  - A Sessionbus daemon through v0.5.12 clears such files when it starts. That is not promised for a later daemon.
- **Dependencies:** the Go SDK moves from `v0.5.9` to `v0.5.12`, the kit from `0.5.9` to `0.5.12`.
- **Versions:** `RELEASE_VERSION` is 0.5.11. The native plugin packages keep their own version, which is independent of it.

## Limits

- **A receipt is not proof of consumption.** `injected`, `queued_for_next_turn` and `written` are receipts from the integration. None of them shows that the model read the message or acted on it, and `written` does not prove a native hand-off. Attempted input is never replayed.
- **OpenCode, cancel with a message pending.** In an interactive session, after the user cancels, OpenCode picks up the pending message and runs it. In a lane, the interrupted task's own message stays in native history, and in the recorded rerun the next Run's model ran that task's command again.
- **OpenCode, a refused lane spawn leaves native state behind:** an empty native session after a fresh spawn, or the title, permission, model and agent updates made before the check after a resume.
- **OpenCode, the same session opened twice.** A second `opencode-peer -s <session> -n <name>` does not take the session over; its `-n` renames the shared session on the bus and in native.
- **Kilo declines some peer requests.** In one interactive session, a request to replace the user's command and two requests to run commands were noticed and declined, citing Kilo's native rule that peer messages are untrusted. The cause is not established.
- **Kilo, permission Reject with a message pending.** The waiting message is submitted as a new turn right after the Reject, as before. Only a native abort holds it.
- **Kilo, a missing native hook is not detected.** Busy delivery relies on an experimental Kilo hook. Nothing checks for or reports its absence or renaming.
- **Kilo, plugin switched off and on in the native plugin manager.** Switching it back on leaves it inactive in that TUI until a relaunch, and Kilo keeps the off setting for later launches until it is turned on again.
- **Kilo lane with an invalid model** ends `unavailable` with a raw `HTTP 500` reason instead of native's model error.
- **A displaced Kilo session keeps an owner slot** of that TUI (128 in all) until the session is deleted natively or the TUI exits.
- **Message envelope.** A literal `</cross-session-message>` in a message body is delivered as `<\/cross-session-message>`, one byte longer, so that the body cannot close the envelope.
- **OpenCode, plugin reload.** The limits of the hand-off are listed with it under OpenCode above. Three more:
  - the hand-off has not been observed across a real reload on a host; it passed its tests against stand-ins only;
  - a rename that OpenCode announces while the session is away is not applied on its return: the session comes back under the bus name it had, and a later rename works as before;
  - a lane whose session is deleted natively in that moment can keep its tool binding until the lane worker ends its endpoint.
- **Not run:** macOS; a native update while sessions are running; a live OpenCode `--resume`; a lane that waits on its own child lane; lane idle wake after a daemon restart.

Known behaviour that is recorded but not fixed is listed in [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).
